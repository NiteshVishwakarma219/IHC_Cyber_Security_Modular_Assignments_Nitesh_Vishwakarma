Security design & limitations

Access control

RBAC is implemented for USER and ADMIN routes. DAC grants resource owners discretion; MAC applies centrally enforced classifications; ABAC evaluates subject, resource and environment attributes. RBAC is selected for this demo because role-based responsibilities are clear and auditable.

Password defenses

  • Adaptive password hashing through Werkzeug's password-hashing API (not plaintext storage).
  • Registration strength checks and a small local weak-password denylist.
  • Five failed attempts in a five-minute window trigger a five-minute lockout for the IP/username pair.
  • Generic login error avoids directly disclosing whether a username exists.

OAuth 2.0 / OIDC

Google sign-in uses the Authorization Code flow through Authlib and Google's OpenID Connect discovery metadata. OIDC supplies identity information on top of OAuth 2.0 authorization. Verified email is required. OAuth is optional until credentials are configured. The application still requires its second-factor checks after federation.

MFA and simulated biometric

TOTP is time-based and compatible with authenticator apps. A second demo input is checked against a stored SHA-256 digest to simulate a biometric factor. It does not perform biometric recognition and should never be described as production biometric security. Real biometric systems should use platform authenticators/WebAuthn and store templates only where necessary with strong protections.

Attack demonstrations and defenses

Use only the local demo: try weak password registration, repeated wrong passwords to trigger throttling, wrong TOTP/biometric inputs, and access /admin as a USER. Defenses include password hashing, strength/denylist checks, throttling, MFA, least-privilege route authorization, secure cookies and audit events.

Production hardening

  • HTTPS only; set COOKIE_SECURE=1 behind correctly configured TLS.
  • Replace the development secret with a random secret from a secret manager.
  • Use Redis/API gateway for distributed rate limiting; the in-memory demo limiter resets on restart and is not multi-worker safe.
  • Add CSRF protection, account recovery, verified-email flow, session revocation, MFA enrollment/recovery, secure secret rotation and alerting.
  • Use a managed identity provider and WebAuthn/passkeys where appropriate. Conduct security testing and privacy review before real use.
